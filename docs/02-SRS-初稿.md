## 二、评价标准

### 2.1 成绩构成（6 分制）

课程每个实验 6 分，其中报告占 20%、答辩占 80%：

- 报告 20% → 6 × 20% = **1.2 分**，分两次提交，**初稿 0.6 + 终稿 0.6**；
- 答辩 80% → 6 × 80% = **4.8 分**，由实验课、理论课、课后抽查三处合并计入。

<p align="center"><b>表 2-7　实验二成绩构成与本次提交的落点</b></p>

| 环节 | 折算 | 课程 100 分制中的分值 | 评什么 | 本稿是否兑现 |
|------|:----:|:--------------------:|--------|:------------:|
| 初稿提交（11-20） | 6 × 20% ÷ 2 | **0.6** | 是否按时交、初稿基线是否完整 | ✅ 本稿 |
| 终稿提交（11-27） | 6 × 20% ÷ 2 | **0.6** | 终稿相对初稿的增量、问题是否闭环 | ⏳ |
| 答辩（三处合并） | 6 × 80% | **4.8** | 现场能否打开 EA/SRS 讲清楚 | ⏳ |
| **合计** | 6 × 100% | **6.0** | — | — |

> **这轮最重要的一句话**：初稿只锁 0.6 分，剩下 98% 的分在答辩。所以初稿的做法是——**每一块都要"能当场打开讲"**，而不是"写得漂亮"。凡是自己讲不清的内容，不要写进来。

### 3.2 五个角色与接口契约

组内 5 人按"数据流上下游"分工，**A 是最上游**（谁都要用它的 diff 与 AST），**B（本人）在 A 之下、C/D/E 之上**——规则引擎的输出是报告与 IDE 诊断的唯一来源，所以 B 的接口一旦定错，下游四个模块全部返工。

<p align="center"><b>表 2-12　五角色分工与接口契约</b></p>

| 角色 | 应用端 / 技术栈 | 核心职责 | 特色 | 对我（B）的依赖 |

| **B-审查规则** | CLI / Python + YAML | **规则管理、权重设置** | **规则市场 + AI 智能审查** | — |
| C-CLI+Web | Python + React + FastAPI | CLI 工具、Web 可视化 | CI 集成 + AI 审查报告 | C 的 CLI **调用**我的 `RuleEngine.execute()` |
| D-报告趋势 | React + ECharts | 报告展示、趋势图表 | 团队统计 + AI 改进建议 | D 消费我产出的 `findings[]` 与 `severity` |
| E-IDE 插件 | TypeScript + VS Code | Patch 生成、一键应用 | TRAE 插件 + AI 自动修复 | E 通过 API 拿我的 `findingId` 生成 Patch |

**我们组定的接口契约（这三条是本学期最贵的经验）**：

1. **`Finding` 是唯一通用数据结构**——A 产出 rawFinding，我加权后补 `severity`/`weight` 字段，C/D/E 只认这一个结构。谁都不许自己另造一份。
2. **规则文件走 YAML，schema 版本号写进文件头**（`schemaVersion: "1.0"`），不然后期加字段会把别人的规则文件读崩。
3. **退出码是契约的一部分**：`0` 通过、`1` 存在 MAJOR 及以上、`2` 执行失败。CI 靠这个码拦截合并，改它就是破坏契约。

| 子加工 | 做什么 | 关键规则 | 对应需求 |

| 后置条件 | 报告落库；`t_review_task.status=DONE` |
| 验收判据 | 10 种 diff 边界（二进制、重命名、纯删除、超大文件等）全部正常；增量审查 P95 < 15 s；退出码语义正确 |

| 项 | 内容 |
|----|------|
| 参与者 | 系统内部触发（被 UC-01 extend）；次级参与者：大模型服务 |
| 前置条件 | 配置了模型端点与密钥；本次任务 `aiEnabled=true` |
| 主流程 | ① 取规则未覆盖的代码块（**先规则后 AI，避免重复付 token**）→ ② 脱敏（去注释中的邮箱/密钥/内部域名）→ ③ 组装 Prompt（角色 + 类别 + 输出 JSON Schema）→ ④ 调用模型 → ⑤ 校验返回 JSON 结构 → ⑥ 丢弃无行号/无证据的结论 → ⑦ 合并进 findings（`source=ai`） |

| 异常流 E3 | 返回的行号不在本次 diff 范围内 → 判定为**幻觉**，丢弃（这是本项目拦得最多的一类错误） |
| 后置条件 | 调用详情（模型名、token 数、耗时、是否降级）写入 D5 日志 |
| 验收判据 | 三类（正确性/性能/安全）各 5 个样例命中率 ≥60%、误报率 ≤25%；**故意关掉模型端点，功能不中断、报告标 degraded**；单次审查 token 成本 < 0.02 元 |
| 备注 | 准确率目前**只有设计没有验证**——标注集要 200 条，安排在实验四做 |

| 关系 | 类型 | 多重性 | 为什么是这种关系 |

| Project → ReviewTask | 关联 | 1 : 0..* | 任务可脱离项目独立存在（如本地临时审查） |

### 8.2 初稿的关键取舍

初稿最典型的问题是**"会写功能、不会写约束"**——第 3 章能写 6,800 字，第 4/5/7/8 章几乎空白。原因是功能需求有现成的用例和访谈支撑，而非功能需求需要"想清楚验证方式"，这件事的难度被严重低估了。

所以本稿做了一个取舍：**宁可第 4、5 章留白，也不写"响应要快、体验要好"这种没法验收的废话**。留白第 2 次课补，写废话后面要返工。
